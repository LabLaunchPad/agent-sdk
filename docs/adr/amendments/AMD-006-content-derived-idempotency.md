# AMD-006 — Idempotency keys are derived from content, not from randomness or position

Resolves [CONFLICT-006](../../architecture/conflicts/CONFLICT-006-idempotency-vs-replay.md).
Amends [ADR-0011](../../../ADR/0011-unknown-outcome-side-effect-state.md).
**Requires [AMD-005](AMD-005-canonical-encoding.md)** — the key is a digest, so it needs a canonical preimage.

| Field      | Value |
| ---------- | ----- |
| Phase      | P00   |
| Supersedes | —     |

## Context

Idempotency keys exist to make a retried external operation safe. The natural implementation — a
random UUID or ULID per operation — is **silently wrong** under crash-resume:

1. The run reaches a payment charge. Generates key `K₁`. Dispatches.
2. The process dies after the provider received the request but before the completion event is appended.
3. The run resumes by folding the log. The operation is re-attempted. A fresh random key `K₂` is generated.
4. The provider sees `K₂ ≠ K₁`, treats it as a new request, and **charges twice.**

This is precisely the failure idempotency exists to prevent, reached by the most obvious reading.
Recording the key before dispatch fixes step 3 only if the append landed before the crash, which
reduces to requiring a durable write per key — and still loses the race between key generation and
its append.

A second trap: deriving the key from the event sequence number. A retry occurring after any
intervening event lands at a different sequence number, producing a different key, defeating
deduplication again.

ADR-0011 already requires that *"every side-effect-capable capability must expose an operation
identity stable enough to support reconciliation after an `UNKNOWN_OUTCOME`."* This amendment
specifies what "stable enough" means, rather than introducing a new requirement.

## Decision

Derive the key from content:

```
idempotency_key = blake3(
    run_id ‖ logical_step_id ‖ capability_id ‖ canonical_cbor(arguments)
)
```

- **Crash-resume safe.** Re-deriving from the same inputs reproduces the same key. Nothing needs
  to have been durably written before dispatch.
- **Replay-exact.** A strict fold reproduces every key without storing it separately.
- **Correct on argument change.** Different arguments yield a different key, which is right: a
  retry with changed arguments *is* a new operation.

`logical_step_id` is deliberately **not** the event sequence number. It identifies the step in the
plan, so a retry after an intervening event still derives the same key. This is the distinction
most easily got wrong, and it is the reason the key is not simply a hash of "where we are".

Because the key is a digest over canonical CBOR, `arguments` inherits AMD-005's constraints —
in particular **no floats**, or the key is not reproducible across encoders.

## Adversarial review

**Attack:** `logical_step_id` is doing the load-bearing work and is not defined here. If plans are
dynamic — regenerated by the model on resume — then step identity is not stable either, and the
scheme fails in exactly the way it claims to fix, only less visibly.

**Failure modes:** a resumed run regenerates a plan whose steps are numbered differently, deriving
fresh keys and double-charging. Or two genuinely distinct operations in a loop share a
`logical_step_id` and the second is silently deduplicated away — a *lost* operation, which is the
mirror-image failure and arguably worse because nothing errors.

**Falsifying experiment:** `crash_resume_rederives_identical_key` covers the primary case. For the
loop case, `distinct_iterations_derive_distinct_keys` — a plan step executed twice in a loop must
produce different keys, which means `logical_step_id` must incorporate an iteration counter.
That requirement is a direct consequence of this review and is stated here rather than discovered
later.

## Alternatives considered

| Alternative | Why rejected |
| ----------- | ------------ |
| Random UUID per operation | Double-charges on crash-resume, as shown above |
| Key derived from event sequence number | A retry after any intervening event derives a different key |
| Durably write the key before dispatch | Still races between generation and append; and it makes every capability call a two-phase write |
| Provider-supplied idempotency key | Not all providers supply one, and it would make the kernel's correctness depend on a provider's semantics |

## Consequences

**Easier:** retries and crash-resume become safe without a pre-dispatch durable write. Strict
fold reproduces keys for free, so the replay proof and the idempotency proof share machinery.

**Harder:** `logical_step_id` must be defined precisely, including loop iterations, and plan
regeneration on resume must preserve it. Arguments must be canonically encodable.

**Foreclosed:** random keys. Sequence-derived keys.

## Revisit trigger

Reopen when a capability's arguments legitimately contain something non-canonicalizable (a
stream handle, a live file descriptor), or when plan regeneration on resume cannot preserve
`logical_step_id`. Either would break the derivation rather than merely inconvenience it.

## Evidence

- **FACT** — ADR-0011 requires an operation identity stable enough to support reconciliation after
  `UNKNOWN_OUTCOME`, and forbids silent retry without first checking actual remote state.
  [`ADR/0011`](../../../ADR/0011-unknown-outcome-side-effect-state.md)
- **INFERENCE** — Content-derivation is the only scheme that satisfies "stable enough" without a
  durable pre-dispatch write, because it is a pure function of inputs the fold already has.
- **UNKNOWN** — Whether `logical_step_id` is stable under model-driven plan regeneration. This is
  the load-bearing assumption and it is unverified; see the adversarial review.
