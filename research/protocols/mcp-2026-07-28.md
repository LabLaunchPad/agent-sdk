# MCP 2026-07-28 Special Audit

> **E4, not E3.** This audit is built from the protocol's own official
> changelog, quoted directly with SEP references — the strongest evidence
> tier available short of running the protocol ourselves. Do not model
> future LabLaunchPad MCP integration around anything older than this
> revision.

## The core shift: MCP is now stateless by design

The single most consequential change: **protocol-level sessions are gone.**
The `initialize`/`notifications/initialized` handshake is removed entirely.
Every request now self-describes its protocol version and client
capabilities via `_meta` (`io.modelcontextprotocol/protocolVersion`,
`io.modelcontextprotocol/clientCapabilities`) rather than establishing them
once at connection time (SEP-2575). The `Mcp-Session-Id` header and
protocol-level sessions are removed from Streamable HTTP entirely
(SEP-2567). List endpoints (`tools/list`, `resources/list`, `prompts/list`)
**no longer vary per-connection** — a server can no longer legitimately
return a different tool list to the same client based on session state.

**Any cross-call state a server needs is now the server's own explicit
responsibility**: "Servers that need cross-call state use explicit,
server-minted handles passed as ordinary tool arguments." This is not an
implementation detail — it is the protocol pushing state ownership out of
its own core and onto the application layer by design.

## Cacheable list results — directly relevant to our Context Gate

`tools/list`, `prompts/list`, `resources/list`, `resources/read` and
`resources/templates/list` now **require** `ttlMs` and `cacheScope` fields
via a `CacheableResult` interface. `ttlMs` is a caching freshness hint;
`cacheScope` (`"public"`/`"private"`) controls whether shared intermediaries
may cache the response. Servers **SHOULD** return tools from `tools/list`
in deterministic order "to enable client-side caching and improve LLM
prompt cache hit rates" — the protocol's own stated reason is prompt-cache
efficiency, which is the exact concern behind this repository's Capability
Discovery Gate ("catalog → match → activate → load detailed schema only
when needed").

## Tasks: graduated to an official extension, redesigned

Tasks moved out of core into `io.modelcontextprotocol/tasks`. The old
blocking `tasks/result` is replaced by polling (`tasks/get`) plus a new
`tasks/update` for client-to-server input during a task. `tasks/list` is
removed. Servers may now return a task handle unsolicited, without
per-request opt-in. This is a **stateless model for long-running work**: no
protocol-level session backs a task, only the handle itself — consistent
with the stateless-core theme above.

## Multi Round-Trip Requests (MRTR) — replaces server-initiated requests

The pattern that replaces `roots/list`, `sampling/createMessage`, and
`elicitation/create` as server-initiated calls: a server returns an
`InputRequiredResult` (`resultType: "input_required"`) whose
`inputRequests` field names what it needs; the client retries the
_original_ request with `inputResponses` supplying it. All results now
carry a required `resultType` (`"complete"` or `"input_required"`) — and
critically, **clients MUST treat results from earlier-protocol servers that
omit the field as `"complete"`**, a specific, deliberate backward
compatibility rule worth replicating in our own protocol adapter's version
handling.

## Authorization hardening

Aligns more closely with OAuth/OIDC: authorization servers SHOULD include
`iss` (RFC 9207) and clients MUST validate it before redeeming an
authorization code; credentials MUST be keyed by issuer identifier and MUST
NOT be reused across issuers; OAuth 2.0 Dynamic Client Registration is
deprecated in favor of Client ID Metadata Documents.

## Deprecations (12-month minimum window, formal policy)

Roots, Sampling, and Logging features are deprecated (still functional,
new implementations should not adopt them) — suggested migrations:
directories/files via tool parameters instead of Roots; direct LLM provider
API integration instead of Sampling; stderr/OpenTelemetry instead of
Logging. HTTP+SSE transport (already deprecated since `2025-03-26`) is now
formally Deprecated. SSE stream resumability (`Last-Event-ID`) is removed
from Streamable HTTP — **a broken response stream now loses the in-flight
request; clients MUST re-issue it as a new request with a new ID.** This
last point matters directly for our own long-running execution model: an
MCP tool call spanning a dropped connection is not resumable at the
protocol level — resumability, if we need it, must be built at the
application layer, not assumed from MCP.

## Implications for LabLaunchPad

### Capability Registry (Phase 8)

Do not design `CapabilityRegistry` around a persistent per-connection MCP
session. The stateless core means our registry's notion of "what tools are
currently available from this MCP server" must be re-derived per request or
cached with `ttlMs`/`cacheScope` respected — not assumed stable for the
life of a connection. `server/discover` (new, mandatory) is the correct
place to learn a server's supported protocol version and capabilities up
front.

### Context Compiler (Phase 6)

The deterministic-tool-ordering requirement and mandatory `ttlMs`/
`cacheScope` fields are a direct, protocol-level endorsement of this
repository's own token-efficiency principle — cache tool catalogs, don't
re-fetch/re-inject them every call. The Context Compiler's capability
catalog for MCP-sourced tools should honor `ttlMs` as the authoritative
staleness signal for that source, analogous to how `x_source_sha256`
governs `.context/` staleness for our own knowledge.

### Long-running execution (State Gate)

MCP's Tasks extension models long-running work as stateless-with-a-handle,
not as a durable session. This is compatible with, but distinct from, this
repository's own Checkpoint/State model — an MCP task handle is not itself
a LabLaunchPad checkpoint, and must not be treated as one. A LabLaunchPad
`RuntimeAdapter` wrapping an MCP-sourced long-running tool call should
persist its _own_ checkpoint referencing the MCP task handle, not rely on
the task handle surviving a connection loss (per the removed SSE
resumability point above).

## A structural distinction worth preserving (decision candidate, not yet an ADR)

MCP's design decisions here reinforce a three-way distinction worth stating
explicitly for Phase 18 (Protocols) rather than silently baking into an
ADR now, since Phase 18 has not started:

```
PROTOCOL STATE   (MCP's own session/connection state — now deliberately minimal)
     ≠
APPLICATION STATE (server-minted handles, task handles — carried explicitly)
     ≠
AGENT STATE      (LabLaunchPad's own Task/State/Checkpoint model)
```

Collapsing these — e.g., treating an MCP task handle as equivalent to a
LabLaunchPad checkpoint, or assuming MCP's connection state implies
anything durable — would be the kind of premature architectural coupling
this repository's dependency-direction rules already guard against in
principle, but this is the first protocol-specific evidence that the
guard matters concretely for MCP. Recorded in
`.context/research/decisions.json` as `ACTION_REQUIRED_AT_PHASE_18`, not
implemented now.
